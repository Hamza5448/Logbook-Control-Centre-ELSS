# Requirement Traceability

This matrix maps the locked ten-requirement scope to implementation modules, GUI screens, observable behaviour, and planned demonstration scenarios.

| SRS requirement ID | Implementation module | GUI screen | Observable behaviour | Planned demonstration/test scenario |
|---|---|---|---|---|
| `Capture-002` | `app.py` (`new_report`, `report_payload_from_form`, `create_report`) and `elss/services.py` (`validate_report_payload`) | **Create Report** | Manual entry of representative Electronic Logbook and Landing Declaration fields with visible required-field validation | Submit a complete Electronic Logbook; submit an incomplete form and observe the exact validation errors |
| `Transmission-002` | `elss/services.py` (`generate_filename`, `next_sequence`) and `app.py` (`create_report`) | **Report Detail** | Automatically generated filename using `[RSSNumber][YYYYMMDD][999999].xml`; UTC date and six-digit zero-padded sequence | Create two reports on the same simulated UTC date and confirm sequence numbers `000001` and `000002` |
| `Transmission-005` | `app.py` (`queue_report`, `send_transmission`, `transmissions`, `transmission_detail`) and `elss/database.py` (`transmissions` table) | **Transmission Monitor** | Explicit `PENDING`, `TRANSMITTED`, `ACKNOWLEDGED`, and `FAILED` states; UTC transmission timestamps; separate acknowledgement status; persisted transmission records | Queue, send, and acknowledge a report; refresh the page and confirm the transmission details remain visible |
| `Acknowledgement-001` | `app.py` (`simulate_acknowledgement`) and `reports`/`transmissions` schema | **Transmission Detail** | Outgoing message IDs and operations are stored; simulated ACKs display `MATCHED` or `UNMATCHED` correlation | Simulate a successful or rejected ACK for a `DAT`/`COR` message and confirm `MATCHED`; simulate an unmatched ACK and confirm `UNMATCHED` |
| `Acknowledgement-002` | `app.py` (`simulate_acknowledgement`) and `templates/transmission_detail.html` | **Transmission Detail** | Successful ACK shows report ID, ACK ID, and accepted status; rejected ACK shows report ID, rejected status, and rejection message | Simulate both successful and rejected ACKs and inspect the displayed acknowledgement details |
| `Correction-001` | `app.py` (`corrections`, `create_correction`, `create_report`) and `elss/services.py` (`build_report_xml`) | **Corrections** | User selects an acknowledged current report, edits fields, generates a `COR` report, and previews the complete XML payload before transmission | Correct an acknowledged report, inspect the complete report XML, queue/send the correction, and simulate an ACK |
| `Frequency-001` | `app.py` (`trip_controls`, `frequency_state`) | **Trip Controls** | Current simulated UTC time, vessel status, catch status, landing declaration status, daily deadline, and frequency-rule state; controlled port, catch, landing-declaration, and time actions | Demonstrate `DUE_BEFORE_DEADLINE`, `SATISFIED_TODAY`, `PORT_EXCEPTION_ACTIVE`, and resumption after **Leave Port** |
| `Capture-005` | All templates and interface text | All screens | English (UK) labels, messages, headings, validation errors, and terminology | Review each GUI screen and validation message for English (UK) consistency |
| `Capture-006` | `elss/services.py` (`format_utc`, `parse_report_datetime`) and all timestamp storage | All screens | UTC timestamps are stored and displayed with an explicit `UTC` label; controlled simulation clock is UTC-based | Inspect report, transmission, acknowledgement, and trip timestamps; set and advance simulation time |
| `Transmission-003` | `elss/services.py` (`encrypt_payload`, `_development_key`) and `app.py` (`send_transmission`) | **Transmission Detail** | Encrypted attachment workflow is shown before simulated transmission using a clearly identified development-only test key | Send a transmission and inspect `Encryption: SUCCESS — development-only key` and the encrypted payload preview |

## Implementation boundary

The prototype does not contact the real UK Fisheries ERS system, does not use production regulatory keys, and does not send real email. The simulated ERS authority is implemented as controlled application behaviour.
